# BVA Analysis for Pawn
# Author: Sebastian Pacheco

**Scope:** Pawn pseudo-legal destination generation for [Issue #38](https://github.com/nu-cs-sqe/cs380-software-quality-engineering-20262701-course-project-group-3/issues/38), part of [User Story #36](https://github.com/nu-cs-sqe/cs380-software-quality-engineering-20262701-course-project-group-3/issues/36). The method returns all destinations allowed by pawn movement and occupancy rules without changing the board. King-safety checks, en passant, promotion execution, applying moves, turn changes, and GUI updates are outside this issue.

**Board conventions:** The source pawn is placed at `from` on `Board.emptyBoard()` unless a standard board is specified. Every unmentioned square is empty. `Location(x, y)` means `(row, column)`; `getX()` returns the row and `getY()` returns the column. For example, `e2 = new Location(6, 4)` and `e7 = new Location(1, 4)`. `W`/`B` identify the subject pawn's color; `F` is a friendly piece and `E` is an enemy piece. Expected destinations in `{}` are **exact unordered coordinate sets**, not Java `Set<Location>` equality assertions, since `Location` does not implement value-based `equals()`/`hashCode()`.

**Pawn movement rules:**

| Pawn color  | Forward row change | Starting row | First advance                    | Starting-row second advance                         |
|-------------|--------------------|--------------|----------------------------------|-----------------------------------------------------|
| White       | -1                 | 6 (rank 2)   | One empty square toward rank 8   | Two squares only if both forward squares are empty  |
| Black       | +1                 | 1 (rank 7)   | One empty square toward rank 1   | Two squares only if both forward squares are empty  |

A diagonal is included only when it is on the board and contains an enemy piece. The result must be non-null, have no duplicate coordinates, and leave the board unchanged. Invalid/null inputs and a source square that does not contain the receiver pawn are **not specified** by Issue #38; exception behavior must be agreed upon before adding tests for them. Each generated list must be asserted as an exact coordinate set (including its size), independent of order. `:x:` marks an unwritten test; replace it with `:white_check_mark:` only when that test passes.
